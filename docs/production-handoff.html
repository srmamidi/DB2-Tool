What goes live

An ASP.NET Core 8 MVC web app hosted in IIS. It reads the Db2 for i catalogs of each environment (Dev, QA, Stage, Prod, and optional replicas) over the IBM i Access ODBC driver, shows every difference, and deploys approved changes through a frozen, hashed script. Data is never promoted, only structure, code and settings.

Before go-live: the live IBM i code has been checked against a fake ODBC driver and by review, never against a real partition. Follow the rollout plan: read-only on Dev first, then deploys into a sandbox library, then QA. Do not point it at Prod until QA has run clean for a full release cycle.

Go / no-go checklist

  1. .NET 8 Hosting Bundle and IBM i Access ODBC driver (64-bit) installed on the web server.
  2. One IBM i service profile per partition, with the authorities in IBM i setup.
  3. Connection strings and secrets in Azure Key Vault; KeyVault:Enabled=true.
  4. Three AD groups (or Entra app roles) created and populated: Developer, Approver, ReleaseManager.
  5. web.config environments, libraries, profiles, IFS paths, deploy windows and distribution edited for your shop (the shipped values are examples).
  6. Turnover:Mode=Live, ASPNETCORE_ENVIRONMENT=Production, Windows authentication on and anonymous off in IIS.
  7. App pool identity has Modify on App_Data; App_Data is included in server backups.
  8. Environments page: Test catalog access is green for every environment.
  9. Package versions in the build match the patched ones listed under Security, and dotnet list package --vulnerable --include-transitive is clean.
  10. Rollout phases 1 to 3 completed and signed off.

A. Side by side under your existing site

The tool runs as its own IIS application at a path of your site (for example https://apps.corp/yourapp/turnover). Users see one site; the two apps share nothing but the host name. All links, redirects and the dashboard's background calls follow the path (tested).

  1. Create an app pool IbmTurnover: No Managed Code, its own identity, Start Mode AlwaysRunning (scheduled deploys need it running).
  2. Publish: dotnet publish src/IbmTurnover.Web -c Release -o D:\Sites\YourApp\turnover.
  3. IIS Manager: on your site, Add Application, alias turnover, physical path above, app pool IbmTurnover.
  4. Stop the parent's settings leaking into the child. IIS passes the parent site's web.config down to every child application; MVC 5 modules, handlers and <system.web> sections break an ASP.NET Core child (HTTP 500.19 / 500.0). In your existing app's web.config, wrap them: 
    <location path="." inheritInChildApplications="false">
  <system.web> ...your existing system.web... </system.web>
  <system.webServer> ...your existing system.webServer... </system.webServer>
</location>
    Keep <appSettings> and <connectionStrings> outside it only if you want them inherited; the tool reads its own web.config.
  5. Authentication on the turnover application: Windows Authentication on, Anonymous off. Users already signed in to your app are signed in here too (same Windows identity).
  6. For Entra ID instead: add the redirect URI https://apps.corp/yourapp/turnover/signin-oidc to an app registration (yours or a new one) and set AzureAd:* in the tool's web.config. Its sign-in cookie is scoped to /yourapp/turnover, so it does not collide with your app's cookie.
  7. Key Vault: point KeyVault:Uri, TenantId, ClientId at the same vault your app uses (you already have these values); set KeyVault:SecretPrefix=Turnover- so only this tool's secrets load.
  8. Give the IbmTurnover app pool identity Modify on turnover\App_Data, and read on the Key Vault certificate's private key.
  9. Add a menu link in your app: <a href="~/turnover/">IBM i Turnover</a> (MVC 5: @Url.Content("~/turnover/")).

Why this is the default: the tool's sign-in rule ("needs a Turnover role") stays inside the tool, its App_Data and deploy lock stay separate, and each app deploys on its own schedule.

B. Embed into an ASP.NET Core 8+ app

Not built yet. This route is a recipe, not a tested build: the tool's screens assume they sit at the application root, so moving them into an Area means rewiring links. Budget the effort above and run the full test suite against the result.
  1. Engine. Reference IbmTurnover.Core (project reference, or pack it as an internal NuGet package). Your app must target net8.0 or later.
  2. Settings. Add the Turnover section and the ConnectionStrings:Db2* entries to your configuration (appsettings, environment variables, or your web.config using the tool's WebConfigSource); secrets in your Key Vault.
  3. Startup (your Program.cs): 
    builder.Services.AddIbmTurnover(builder.Configuration, builder.Environment.ContentRootPath);
builder.Services.AddHttpContextAccessor();
builder.Services.AddSingleton(new RoleGroups(roleGroups));          // Turnover:RoleGroups
builder.Services.AddSingleton(new AuthSettings(AuthMode.Windows));  // or EntraId
builder.Services.AddScoped<ICurrentUser, CurrentUser>();
builder.Services.AddHostedService<AutoSnapshotService>();
builder.Services.AddHostedService<ScheduledDeployService>();
builder.Services.AddAuthorization(o => o.AddPolicy("Turnover", p => p.RequireAuthenticatedUser()
    .RequireAssertion(ctx => CurrentUser.RolesFor(ctx.User, roleGroups).Count > 0)));
...
app.Services.GetRequiredService<SnapshotService>();   // starts snapshot history
app.MapAreaControllerRoute("turnover", "Turnover", "turnover/{controller=Home}/{action=Index}/{id?}");
  4. Do not copy the tool's global rules. Its Program.cs sets a fallback policy (every page needs a Turnover role) and a site-wide CSP. In your app those would lock your own pages. Use the Turnover policy above instead.
  5. Web layer into an Area. Copy Controllers/Controllers.cs, Models/ViewModels.cs, Infrastructure/{CurrentUser,Ui,AutoSnapshotService,ScheduledDeployService}.cs and Views/** to Areas/Turnover/. On the TurnoverController base class add [Area("Turnover")], [Authorize(Policy = "Turnover")] and [AutoValidateAntiforgeryToken]; do the same on AccountController (status pages, keep it anonymous). The Area also stops the tool's HomeController and AccountController clashing with yours.
  6. Links. Views build links as @Url.Content("~/")Compare (application root). Inside an Area change that prefix to @Url.Content("~/turnover/") (one search-and-replace across the views), set <body data-base="@Url.Content("~/turnover/")"> in the layout, and change the controllers' LocalRedirect("~" + ...) calls to "~/turnover" + ....
  7. Static files. Copy wwwroot/css/site.css and wwwroot/js/{site,theme}.js to wwwroot/turnover/ and update the two layouts. Either keep the tool's own layout (simplest) or move its header and nav into yours; its styles are not namespaced, so check them against your CSS.
  8. Storage. Packages, check-outs, snapshots and source history are JSON files under your app's App_Data, and the deploy lock is in memory: your app must run as a single instance, or implement ITurnoverRepository, ICheckoutStore, ISnapshotStore and ISourceArchive on your database first.
  9. Packages. Keep at or above the tool's versions: Microsoft.Identity.Web 3.15.1, Negotiate 8.0.31, Azure.Identity 1.13.1, System.Security.Cryptography.Xml 8.0.4.
  10. Prove it. Port tests/IbmTurnover.Tests web tests to your app's test project (pages render, POST forms carry the anti-forgery token, no link leaves /turnover/, a user without a Turnover role gets 403 on Turnover pages and still reaches your pages).

Today the same connection string is used for reading and deploying. If your security team wants a read-only profile for comparisons, that needs a second connection string per environment (not built yet).

Connection string

Driver={IBM i Access ODBC Driver};System=IBMPRD01;UID=TOVSVC;PWD=...;NAM=0;CMT=0;SSL=1;

NAM=0 (SQL naming) and CMT=0 (no commitment control) are required; the app refuses a string that sets them otherwise and adds QueryTimeout=0. Store the whole string as a Key Vault secret named ConnectionStrings--Db2Prod (two hyphens).

Housekeeping on IBM i

  • Backup libraries TB* accumulate, one per deployed package. Delete them after the package's retention period (suggest 90 days), e.g. a monthly job on each partition.
  • IFS backups sit beside the file as name.TBnnnnnnnn; clean them up the same way.
  • Job queues named in PreDeployCommands must exist on every partition that uses them.

IIS

  1. Application pool: No Managed Code, Integrated pipeline, identity = a domain service account (or ApplicationPoolIdentity if Key Vault uses a certificate it can read).
  2. Site or application pointing at the publish folder; HTTPS binding with the certificate.
  3. Authentication (Windows login): enable Windows Authentication, disable Anonymous. Set this in IIS Manager; the server locks these sections, so web.config cannot.
  4. Environment variable on the app pool or in web.config <aspNetCore>: ASPNETCORE_ENVIRONMENT=Production.
  5. Create App_Data under the site and give the app pool identity Modify rights.
  6. Key Vault with a certificate: install it in LocalMachine\My and grant the app pool identity read on its private key.
  7. Optional: set stdoutLogEnabled="true" for the first start only, to see startup errors in logs\stdout.
  8. The app can be a root site or an IIS application under a path (e.g. /turnover); links follow the path. If Windows Authentication is not enabled on the site, every request fails: enable it in IIS Manager first.

First start

The app validates everything at startup and refuses to run on a bad environment map, missing connection string, missing role group, Demo mode in Production, or a misconfigured Key Vault. A 500.30 on first start means read the stdout log or the Windows Application event log for that message.

Upgrade

  1. Check no package is Deploying and none is scheduled in the next hour (Packages page).
  2. Copy App_Data to a dated backup.
  3. Drop app_offline.htm into the site, publish over the folder, remove it.

Daily running

  • Scheduled deploys run from a background job every minute. If the app pool recycles or idles, they wait: set the app pool Start Mode to AlwaysRunning and the site to Preload enabled, idle time-out 0.
  • Workflow page shows every catalog read, how long each query took and which failed.
  • Logs: ASP.NET Core logs go to the Windows event log / stdout. Forward them to your log platform; scheduler failures log as errors.

When a deploy fails

  1. Open the package, Runs tab: the failed step and the IBM i message (CPF/SQL code) are shown. Later steps were skipped; Finally steps (release job queue) still ran if their command had run.
  2. Fix the cause on IBM i if it is environmental (lock, authority, missing job queue).
  3. Either Roll back (undoes completed steps in reverse, in the target and any replicas) or fix forward by hand. There is no "resume from failed step" yet.
  4. Re-submit: the target changed, so the old approval no longer matches and a new one is required.

When a package is stuck in Deploying or RollingBack

Only possible if the app stopped mid-run (server restart, app pool recycle). Check the Runs tab and the objects on IBM i, then a release manager uses Mark failed on the package (a note of 20+ characters is required and audited) and rolls back or fixes by hand.

"Changed by someone else a moment ago"

Two people acted on the same package at once; the second save was refused so neither is lost. Reload the page and repeat the action.

Controls in place

  • Fails closed: bad config, a failed catalog read, a missing role or an unreachable Key Vault stops the action or the app.
  • Every page needs a signed-in user with at least one Turnover role; every action checks its role in code, not only in the UI.
  • Separation of duties: requester cannot approve; requester cannot deploy own package to Stage/Prod; 2 approvals for Prod.
  • Deploy runs only the frozen approved script, and refuses if the target or a replica changed since approval.
  • Passwords are never copied; secret-looking data-area values and key/certificate files are masked or left unticked; security system values are blocked.
  • Antiforgery tokens on every POST, CSP without inline script, HSTS, X-Frame-Options DENY.

To do before go-live

  • Done in this release: Microsoft.AspNetCore.Authentication.Negotiate 8.0.31, Microsoft.Identity.Web 3.15.1 and System.Security.Cryptography.Xml 8.0.4 (pinned; it came in transitively with a high-severity advisory). Re-check before go-live; new advisories appear.
  • Set KeyVault:SecretPrefix (e.g. Turnover-) when the vault is shared, so other applications' secrets are not loaded as settings.
  • Entra ID: users in more than about 200 groups get no groups claim. Use app roles named Developer / Approver / ReleaseManager instead of group ids.
  • Add the app to your vulnerability scanning (SCA) and patching cycle; .NET 8 is supported until November 2026, so plan the move to .NET 10.
  • Review custom steps as code: approvers must read them, they run with the service profile's authority.
