IBM i Turnover — environment propagation for Db2 for i

159 tests passing.NET 8 · ASP.NET Core MVCLive mode: verify on your releasev1.2

What it is

A turnover tool for IBM i. It compares two environments (Dev, QA, Stage, Prod — each with several libraries), explains in plain words what would break if you promoted the difference, and builds an ordered script that moves it safely: pre-checks, backups, DDL, source copy and compile, routines, post-checks, and a rollback for every step.

It ships as two pieces: IbmTurnover.Core, a class library you can add to any ASP.NET MVC / C# application with one line, and IbmTurnover.Web, a complete MVC front end.

Compare & propagate

Dev → QA → Stage → Prod, one tier at a time. Logical libraries map to physical ones per environment (ORDERS = ORDDEV / ORDQA / ORDSTG / ORDPRD).

Library → library

Copy object definitions between two libraries on the same IBM i, rewriting library names inside procedures, views and triggers.

Library move

Move or clone a whole library with its data (CPYLIB) and re-point every foreign key, view and procedure in other libraries that names it.

Everything except data

Tables, columns and data types, keys, foreign keys, indexes, sequences, aliases, check constraints, procedures, functions, views, triggers, RPG/CL/DDS/commands, data areas and queues, job descriptions, messages, user profiles and service accounts, object authorities and owners, menus and panel groups, binding directories, authorization lists, job schedule entries, system values and IFS stream files.

Deploy control

Lock checks before changes, deploy windows, scheduled and emergency deploys, pre/post CL per environment (e.g. hold and always release a job queue), custom conversion steps, and distribution to DR / HA replicas.

Snapshot history

Every live read is recorded (unchanged structure costs nothing). Compare any two points in time, or a snapshot with live.

Governed packages

Draft → Submitted → Approved → Deployed. Requester cannot approve; Prod needs two approvers; the approved script is frozen and hashed.

Flow

Order of a deployment

Setup (backup library, library list, pre-deploy commands such as HLDJOBQ) → pre-checks that must return 0, including object-lock checks on everything changed in place → backups (CRTDUPOBJ with data, source members) → sequences → tables → column changes → indexes → foreign keys → source copy and compile (service programs first, then level-check recompiles) → functions, views, procedures, triggers in dependency order → custom steps at their point → post-checks that the objects exist → Finally steps (release the job queue, post-deploy commands), which run even after a failure.

Safety rules built in

  • Configuration is validated at startup: bad library names, two environments sharing a library on one host, or missing Live connection strings stop the app.
  • A catalog read that fails part-way throws; it never returns a partial snapshot that would make objects look removed.
  • Deploy refuses if the target changed since approval (fingerprint) or the script differs from the approved one (hash).
  • Rollback undoes the frozen approved steps that actually ran, in reverse order.
  • Prod cannot override blockers; lower tiers need a written justification.
  • The source text that was approved is pinned in the script: source edited after approval no longer matches and the deploy is refused. If the script changes between submission and the last approval, approvals are reset.
  • One deployment or rollback per environment at a time; once steps start they run to the end even if the browser is closed, and the run is always recorded.
  • Two people acting on one package at once: the second save is refused instead of silently overwriting the first.

Add to an existing MVC app

// Program.cs
builder.Services.AddIbmTurnover(builder.Configuration, builder.Environment.ContentRootPath);

// any controller
public class MyController(TurnoverService turnover) : Controller
{
    public async Task<IActionResult> Drift() =>
        View(await turnover.CompareAsync("DEV", "QA", ["ORDERS", "CUSTOMER"]));
}

Copy the Views, wwwroot/css/site.css and wwwroot/js/site.js from IbmTurnover.Web if you want the same screens. Replace JsonFileTurnoverRepository with your own ITurnoverRepository to store packages in your database.

Where settings live

All settings are in web.config (<appSettings> and <connectionStrings>), editable in IIS Manager. Order, later wins: appsettings.json, web.config, environment variables, Azure Key Vault.

Run locally

launcher\run-local.bat

launcher\ holds run-local.bat, run-dev.bat and run-prod.bat; every setting is in the matching .env file next to them.

Set ASPNETCORE_ENVIRONMENT=Development and Turnover__Auth__Mode=Demo for the demo users (alice developer, bob and carol approvers, dave release manager); web.config itself asks for Windows login. If only a newer .NET runtime is installed, also set DOTNET_ROLL_FORWARD=Major; servers should have the .NET 8 runtime.

Known limits

  • Live catalog SQL follows IBM's QSYS2 documentation but has not been run against a real IBM i here. Use Environments → Test catalog access on each partition first.
  • A sequence's next value cannot be read without using it up, so in Live mode the check runs as a deploy-time pre-check (consumes one value).
  • RPG source is hashed, not parsed: field-level use of a renamed column inside RPG is flagged as a warning, not proven.
  • Multi-module programs, unknown languages and DSPF / PGM menus are listed as manual builds.
  • Not compared: SQL packages, subsystems, exit programs, data. A failed deploy cannot resume from the failed step.
  • Packages, check-outs and snapshots are JSON files and the deploy lock is in memory: run one web server.
  • Sample mode simulates deployments; nothing is sent to IBM i.
